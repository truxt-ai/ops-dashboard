## Verification and exposure

The unchanged baseline passes 62/62 tests and lint. The three final HTTP cases
run against an archived baseline with its original lockfile: the bounded-query
regression fails the expected array/object assertion, while both compatibility
controls pass. The identical test file passes 3/3 after the upgrade, and the full
candidate suite passes 65/65 with lint passing. No build script is configured.
Local HTTP uses ephemeral loopback ports. Existing readiness tests mock axios;
no live upstream availability or deployment was tested.

The red/green case is an explicit test-only Express fixture with qs arrayLimit=5,
covering GHSA-6rw7-vpxm-498p. It is dependency proof, not evidence of a production
DoS. Production Express sets arrayLimit=1000 and retains parameterLimit=1000;
production routes do not inspect query data. A discarded initial test incorrectly
expected a 22-item array to exceed that limit; its failed candidate run is retained,
and the corrected final reproduction was rerun on both versions before acceptance.
The advisory also documents parameterLimit's mitigation:
[maintainer advisory](https://github.com/ljharb/qs/security/advisories/GHSA-6rw7-vpxm-498p).

The app has no body-parser middleware, redirects, static serving, parameterized
routes, custom trust proxy, or qs.stringify call sites. The proxy control confirms
default trust proxy=false ignores forged forwarding headers. The app compatibility
case checks actual liveness/promo GET requests, HEAD, suspicious query keys, and 404
path/method behavior. Other selected findings are proven removed by resolved-version
readback and both scans, without claiming end-to-end exploit reproductions.
